# 国内情報漏えい台帳：過去分の収集・照合（1か月分を担当）

DIR = リポジトリ内の backfill フォルダ（クローンした leak-ledger-data/backfill）

あなたの担当は指定された1か月（YYYY-MM）です。その月に初めて公表された、国内の組織の個人情報の漏えい・漏えいの可能性の事案を集め、1件ずつ組織自身の公式発表を開いて照合します。

## 参照ファイル
- DIR/existing.txt … すでに台帳にある事案（日付・id・組織名）。同じ事案は追加しない（続報も追加しない）。
- DIR/labels.json … items・industries・cause・who に使える値。
- DIR/example.json … 1件のレコード例（この形で書く）。

## 出力（必ず逐次書き込む）
- 照合できた事案：DIR/out/YYYY-MM.verified.jsonl に 1行1件の JSON（example.json と同じキー）。1件確定するたびに追記する（Bash の `>>` か、Python で追記）。
- 照合できなかった候補：DIR/out/YYYY-MM.pending.jsonl に 1行1件。verified の代わりに "pendingReason"（公式発表が見つからない／開けない／内容が食い違う など具体的に）。わかる範囲の項目だけでよい。
- 終わったら DIR/out/YYYY-MM.done に「verified件数 pending件数 確認した候補数」を1行書く。
- 最後の返答は短く（件数と、気になった点だけ）。JSON を返答に貼らない。

## 候補の集め方（その月に初回公表されたもの）
1. ScanNetSecurity のインシデント記事一覧：https://scan.netsecurity.ne.jp/category/incident/YYYY/MM/?page=1 から全ページ（「Page 1 of N」を確認）。翌月1〜2ページ目も見て、その月に公表された事案の遅れ掲載を拾う。
2. Web検索で補う（月を付けて）：「YYYY年M月 個人情報 漏えい 不正アクセス」「YYYY年M月 ランサムウェア 個人情報」「YYYY年M月 個人情報 紛失」「YYYY年M月 誤送信 個人情報」など4回以上。
3. 記事が続報の場合は、初回公表日がその月でなければ対象外（別の月の担当が拾う）。

## 照合（大原則）
- 組織自身の公式発表（自社・自組織サイトのお知らせ、IR、PDF、TDnet）を WebFetch で実際に開き、件数・内容が記事と一致したものだけを verified にする。推測で埋めない。確認の許可はすでに得ているので、リンクはすべて自分で開いてよい。
- 公式発表が見つからない、開けない（robots・JS・PDFエラー）、内容が食い違う → pending。
- 続報（調査結果・最終報・件数確定）が公式に出ていれば、それも開いて反映し、"last" に続報の日付、official に追加。status は調査結果・最終報・処分が出ていれば "closed"。

## 対象
- 国内の組織（企業、国・自治体・警察などの公共機関、大学・学校、病院、団体。子会社・委託先・海外拠点を含む）の個人情報の漏えい・漏えいの可能性。原因：サイバー攻撃（ランサムウェア、不正アクセス、委託先経由、サポート詐欺など）、紛失・盗難、誤送信・誤掲載、内部不正、設定ミス・システム不具合のすべて。
- 対象外：漏えいに触れていない障害・改ざん、迷惑メール送信のみ、犯行声明のみ、海外企業のみの事案。
- 個人（行為者の職員など）の氏名は書かない。

## 各キーの書き方
- id：英小文字・数字・ハイフン。組織名のローマ字＋必要なら年月（例 "gaora-shop-2411"）。existing.txt と重複させない。
- co：組織名（サービス名は（）で）。date：初回公表日 YYYY-MM-DD（発生・検知日が明確ならそれでも可。迷ったら初回公表日）。
- cause：cyber / loss / mis / insider / config。types：cyber なら "ランサムウェア"・"不正アクセス"・"委託先経由" から（複数可）、それ以外は causeLabels の表示名1つ（例 ["紛失・盗難"]）。
- n：数値（人数または件数。最大値で）。不明なら null。label：表示用（例 "約1.5万件"、"最大3,210人"、"調査中"）。
- st："c"＝漏えいを確認、"p"＝漏えいの可能性。
- items：labels.json の itemLabels のキー。公式発表に書かれた項目だけ。itemsText：項目を公式発表どおりに短く。notIncl：含まれないと明記された情報（なければ ""）。
- who：cust（顧客・利用者・会員・患者・学生・住民など）、biz（取引先・法人顧客・代理店の担当者など）、staff（従業員・職員・退職者・家族・自組織への応募者）、work（個人情報以外の業務情報）、unk（区分の記載なし）。該当するものすべて。推測しない。
- sum：何が起きたかを自分の言葉で2文以内。記事の文章や見出しを写さない。
- status / statusText：根拠を短く。resp：組織の対応（通知、窓口、停止、再発防止策、報告など）を自分の言葉で。
- contact：公式発表に書かれた本件の問い合わせ窓口。{"tels":[{"tel":"0120-...","hours":"平日9〜17時"}],"mails":[...],"forms":[["表示名","URL"]],"note":"部署名など","src":"窓口が載った公式発表URL"}。空のキーは省く。報道機関向け窓口は入れない。記載がなければ {"note":"公式発表に窓口の記載なし","src":"公式発表URL"}。
- official：[["公式発表の名前（YYYY/M/D）","URL"]]。src：[["報道機関名","記事URL"]]（見出しではなく媒体名だけ）。
- ind：labels.json の industries から1つ（公共機関＝国・自治体・警察・独立行政法人、団体＝協同組合・財団・社団・NPO・協会など）。
- verified：作業した日の日付（日本時間）。claim（犯行声明）は公式発表や報道にあれば任意。

## 進め方のコツ
- 1件ずつ「記事を見る → 公式発表を探して開く → 1行追記」を繰り返す。まとめて最後に書かない。
- 公式発表が自社サイトから消えている古い事案は、Web検索で PDF の URL を探す。見つからなければ pending。
- 1件にかける fetch は最大4回程度。迷ったら pending にして次へ。
