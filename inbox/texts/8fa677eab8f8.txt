Zeabur 2026年10月のセキュリティインシデント（初期報告）
攻撃者が共有クラスターとGCPのDedicated Serverに侵入し、Zeaburのプラットフォームデータベースに保存されていた環境変数を読み取りました。本記事では、何が起きたのか、どのデータが影響を受けたのか、当社が行った対応、そしてお客様に必要な対応について説明します。

概要
何が起きたのか：
 2026年10月14日から15日にかけて、攻撃者は流出したZeaburの内部認証情報を使用して、共有クラスター、一部のDedicated Server、Zeaburの内部システムに侵入し、最終的にプラットフォームデータベースを読み取りました。
遮断済みの侵入口：
 攻撃者が使用したクラスター管理トークン、AWSとGCPのキー、内部ネットワークのノードはすべて失効または削除済みで、管理インターフェースとサーバーへのインターネットからのSSHは遮断しました。すべてのユーザーをログアウトさせ、プラットフォームのアクセストークンもすべて失効させています。現在の記録では、攻撃者の最後の活動は10月15日 21:05です。
影響を受ける対象：
 主に
共有クラスター上のサービス
と
GCPのDedicated Server
です。Zeaburのプラットフォームデータベースに保存されていた環境変数も読み取られました。8月以降、案内に従って環境変数をご自身のDedicated Serverに移行したプロジェクトでは、それらの変数はプラットフォームデータベースが読み取られた範囲に含まれません。
お客様に必要な対応：
 流出したデータは引き続き悪用される可能性があります。8月のインシデント後にすでに差し替えた場合でも、Zeaburに保存しているすべてのパスワードとキーを差し替えてください。手順は
お客様に必要な対応
をご覧ください。
根本原因：
 本インシデントの根本原因はZeaburにあります。長期間有効な管理用認証情報が平文で保存され、インターネットから使用できる状態でした。詳しくは
発生の原因
をご覧ください。
8月のインシデントとの関係：
 8月のローテーションは、今回使用された認証情報を対象にしていませんでした。一方、8月の案内に従って環境変数を移行したプロジェクトは、プラットフォームデータベースからの流出を免れました。詳しくは
8月のインシデントとの関係
をご覧ください。

何が起きたのか
攻撃者は2つの経路をたどり、最終的にZeaburの内部ネットワークで合流しました。
経路A：共有クラスターとAWS
10月14日 01:36から攻撃者はZeabur内部のAWSキーを、01:40から共有クラスターの管理トークンを使用しました。これらの認証情報は、Zeaburのプライベートな設定リポジトリに平文で保存されていました。攻撃者がこれらをどのように取得したかは、現時点で
確認できない
状態です。当社は、8月のインシデントで流出したGitHub Appの秘密鍵が関係していると推測しています。
未証明の推測
をご覧ください。
共有クラスターの管理インターフェースは当時インターネットに公開されており、管理トークンにも有効期限がありませんでした。このため攻撃者は、外部から9つのリージョンの共有クラスターにアクセスできました。
01:51から、攻撃者は一部のシステムシークレットを読み取りました。12:39からは、範囲が環境変数を含むすべてのサービスの設定とシークレットに広がりました。完全な読み取り記録があるリージョンでは、内容が読み取られたことを確認しています。その他のリージョンは記録が欠けているため、すべて流出したものとして扱っています。
13:40から、攻撃者はユーザーのデータベースのコンテナ内で読み取りコマンドを実行しました。まず少数のnew-api／one-apiに対して行い、15:41からn8nを大量に読み取り、16:50から一部のPostgreSQLをテーブルごとに読み取りました。最後のコマンドは17:04です。攻撃者がコマンドを実行したデータベースサービスは計865個ですが、すべてのコマンドが成功したわけではありません。
攻撃者は、クラスター内にあった別の権限過大なキーを使用して、旧クラスターのバックアップを読み取りました（
推定
）。バックアップには、Zeaburのシークレット管理サービスを読み取れるキーが含まれていました。
10月15日 14:52から16:51にかけて、攻撃者は約53件の本番環境シークレットを読み取りました（
確認済み
）。その中には、内部ネットワークの管理用認証情報、プラットフォームデータベースのアカウント、GitHub Appの秘密鍵が含まれていました。
経路B：GCPのDedicated Server
10月14日 13:40から、攻撃者はZeaburがGCP上で管理するDedicated Server計101台にrootとしてログインしました。
これらのサーバーの初期化設定には、rootパスワードが平文で保存されていました。攻撃者は、この設定を読み取れる古いGCPキーを保持していました。当社は、攻撃者がこのキーでパスワードを取得したと
推定
しています。
10月15日 14:26から、攻撃者は古いGCPキーでサーバーの設定を変更し、自身のSSH鍵を追加しました。15:05には、シークレット管理サービスから本番環境のGCPキーをさらに1つ取得しています。当社が17:17に古いキーを無効化した後、攻撃者は17:28にこのキーに切り替えて再びSSH鍵を追加しましたが、当社は17:31にこのキーも無効化しました。10月14日のGCPサーバーへの最初のログインは、10月15日に本番環境シークレットが読み取られた最初の既知の記録より前に発生しています。後者を前者の起点と記述することはできません。
それ以前の9月1日から5日にかけて、出所不明の送信元が同じ一群のサーバーにrootパスワードでログインしており、9月5日当日は約98台でした。同一の攻撃者かどうかは、現時点で
確認できない
状態です。
2つの経路の合流
10月15日 15:30、攻撃者は侵入したGCPサーバーの1台で、経路Aで取得した内部ネットワークの管理用認証情報を使用し、1つのノードをZeaburの内部ネットワークに参加させました。
内部ネットワークのルールでは、この種のノードからプラットフォームデータベースへの接続が許可されていました。16:10から16:47にかけて、攻撃者は内部の読み取り専用アカウントでプラットフォームデータベースを読み取りました（
確認済み
）。当社は内部ネットワーク両端の接続記録とデータベースのログを突き合わせました。この期間の29件のデータベース接続はすべてこのノードに対応しており、接続内のログインとクエリも一件ずつ追跡でき、操作記録は計8,903件でした。
17:58、当社はこのノードを削除しました。

プラットフォームデータベース。
 10月15日 16:10から16:47にかけて、攻撃者は上表のデータを読み取りました。アカウントのデータには、メールアドレス、ユーザー名、電話番号など、プロフィールページ上の情報が含まれます。攻撃者は、環境変数と設定ファイルからAPIキーと秘密鍵も検索しました。コマンドの内容とその後の行動から見ると、攻撃者は主にそのまま使用できるAPIキー、特にAIサービスのキーを探していました。攻撃者はプラットフォームデータベースでキーを検索し、n8nとnew-api／one-apiの認証情報を大量に読み取り、ZeaburのAWSキーでAmazon Bedrockの呼び出しも試みています。これは攻撃者の意図についての観察にすぎません。攻撃者はアカウントのデータも読み取っており、当社は読み取られたすべてのデータを流出したものとして扱っています。二要素認証とパスキーのテーブルについては統計情報が照会されたのみで、内容が読み取られた記録はありません。当社はすべてのユーザーのプラットフォームのアクセストークンを失効させており、古いトークンはいずれも使用できなくなっています。
移行済みの環境変数は、プラットフォームデータベースが読み取られた範囲に含まれません。
 8月のインシデント後、ZeaburはDedicated Serverをご利用のお客様に向けて、認証情報のローテーション、Zeaburに保存している環境変数と設定ファイルの削除、およびご自身のサーバーへのワンクリック移行についての案内と機能を提供しました。移行を完了したプロジェクトでは、これらのデータはお客様のサーバー上にのみ保存され、Zeaburは保持していないため、今回プラットフォームデータベースから読み取られたデータには含まれません。移行していないプロジェクトでは、環境変数がZeaburに保存されたままであり、今回読み取られました。これはホストへの侵入による流出を否定するものではありません。侵入されたGCPのDedicated Serverには、引き続き下記の対応をお勧めします。
アカウントのなりすまし。
 攻撃者はログイン用の認証情報を発行するためのキーを読み取っており、当社は攻撃者がこれを使ってログイン用の認証情報を偽造したと
推定
しています。攻撃者がプラットフォームのアクセストークンを大量に読み取ったのは16:47になってからであり、しかもトークンはハッシュ値のみが保存されているため、16:12に始まったなりすましは説明できません。10月15日 16:12から17:19にかけて、攻撃者は2つのアカウントになりすましてZeabur APIを呼び出し、アカウントとプロジェクトの一覧を読み取りました。そのうち1つはZeabur従業員のアカウントです。これらのリクエストでリソースが変更されたことはありません。当社は20:25に署名キーをローテーションし、すべてのユーザーをログアウトさせました。

GCPのDedicated Server。
 調査の結果、攻撃者が101台のサーバーにroot権限でログインしていたことを確認しました。最後のログインは10月15日 20:36です。攻撃者はそのうち50台のサーバーに自身が管理するSSH公開鍵を追加し、継続的なアクセス経路を確保していました。また、ZeaburのGCPプロジェクト内に仮想マシンを5台作成し、16件の顧客サーバーのディスクのコピーをそれらの仮想マシンにマウントしていました。
このアクセス範囲を踏まえ、これら101台のサーバーはすべて、データ流出および不正アクセスの仕組みが残されている可能性がある影響対象ホストに分類しています。影響を受けたユーザーにはメールでお知らせし、該当サーバーのrootパスワードをリセットしました。
HetznerとDigitalOcean。
 この2社のお客様のサーバーを管理するトークンは内部のコードと環境変数に記載されており、プラットフォームデータベースとともに流出しました。トークンを保持していれば、パスワードのリセット、OSの再インストール、ディスクの複製が可能です。当社は10月16日 01:09にすべてのトークンを失効させました。2社とも操作の監査ログがありません。Hetznerアカウントのイベントはすべてユーザーご本人またはシステムのスケジュールに対応しており、DigitalOceanは引き続き照合中です。
LinodeとTencent Cloud。
 Linodeの890台のサーバーのうち、記録がある847台には攻撃者のログインはありませんでした。Tencent Cloudの管理用認証情報には、使用された記録はありません。
GitHub App。
 攻撃者は10月15日 15:05にZeabur GitHub Appの秘密鍵を読み取りました。秘密鍵を保持していれば、ユーザーがZeaburにアクセスを許可したリポジトリにアクセスできます。当社は18:54に秘密鍵をローテーションしており、現時点で使用された形跡は見つかっていません。GitHub Supportに完全な監査ログを申請していますが、まだ回答を得ていません。
Zeaburの内部システム。
 攻撃者はZeaburのAWSキーを複数使用しました。大部分のリクエストは拒否されましたが、攻撃者は2つのリージョンのユーザーのデータベースのバックアップと、ソースコードのアップロードの内容を一覧表示しました。ダウンロードしたかどうかは

発生の原因
発端：
 攻撃者は、Zeaburのクラスター管理トークンと複数のクラウドのキーを保持していました。これらの認証情報は、設定リポジトリに平文で保存されていました。攻撃者がこれらをどのように取得したかは、現時点で確認できません。最も可能性の高い経路は
未証明の推測

影響範囲が拡大した関連要因：
管理トークンのライフサイクルとインターフェースのアクセス制御。
 管理トークンには有効期限が設定されておらず、2024年1月の作成以来一度もローテーションされず、8月のインシデント後のローテーション対象にも含まれていませんでした。管理インターフェースはインターネットからアクセス可能でした。
シークレットの保管と改善の進捗。
 設定リポジトリ、コード、共有クラスターのサービス設定およびビルドジョブに、平文で保存されたキーが存在していました。GCPサーバーの初期化設定にもrootパスワードが保存されており、この問題は9月3日に特定されていましたが、インシデント発生前に修正は完了していませんでした。10月3日に開始したシークレット移行の変更は、インシデント発生時点でメインブランチにマージされていませんでした。
バックアップの内容とキーの分離。
 クラスターのバックアップにはすべてのシークレットが含まれ、バックアップのアクセスキーが他のシークレットと同じ環境に保管されていたため、バックアップ内容へのさらなるアクセス経路となりました。インシデント対応中にローテーションした一部の認証情報も、その後のバックアップに含まれていました。
アクセス権限とリソースの範囲。
単一のストレージの読み取りだけが必要なキーが、実際にはAWSアカウント内のすべてのストレージを読み取れる権限を持っていました。
GCPサーバーのデフォルトのサービスアカウントが、プロジェクトレベルの変更権限を持っていました。
内部ネットワークのルールが、特定のタグを持つノードからプラットフォームデータベースへの接続を許可していました。
内部の読み取り専用データベースアカウントが、すべてのデータを読み取れる権限を持っていました。
停止済みサービスのデプロイキーが、サービス停止から4か月後も有効でした。
内部サービスとユーザーサービスの環境分離。
 両者が同じクラスターにデプロイされていたため、攻撃者はユーザー設定を読み取る際に、内部サービスの認証情報も取得できました。
検知と監査ログの対象範囲。
 10月14日に16時間以上続いた攻撃活動はアラートを発生させず、翌日ユーザーからの報告を受けてインシデントを特定しました。ストレージ、GCP、GitHubのアクセス記録が不完全なため、一部のアクセスと影響範囲は現在も確認できていません。
8月のインシデントとの関係
これは、Zeaburにとって2か月足らずのうちに起きた2件目のセキュリティインシデントです。8月以降、当社の案内に従って対応を行ったユーザーの方も多く、そうした対策を講じたのになぜまた起きたのか、2件のインシデントに関係はあるのか、という疑問をお持ちのことと思います。
8月以降に行ったこと。
 当社は、当時流出が確認された内部キーをローテーションし、Legacy API Keyを廃止しました。プロダクト面では、Dedicated Serverのプロジェクトで環境変数と設定ファイルをご自身のサーバーに移行できるようにし、Zeaburが保持するSSH認証情報の削除と、SSHログイン記録の確認もできるようにしました。8月のインシデントの通知とお知らせでも、認証情報のローテーション、Zeaburに保存している環境変数と設定ファイルの削除、ご自身のサーバーへの移行をお勧めしていました。

 攻撃者は、8月のインシデントで流出したGitHub Appの秘密鍵を利用して、Zeaburのプライベートな設定リポジトリの内容を取得した。その中には、10月14日に使用されたAWSキーとクラスター管理トークンが含まれていた。
現時点で、この経路を直接証明する証拠はありません。
 以下は、時期と能力の面で一致する間接的な手がかりにすぎません。
差し替えたものと差し替えていないもの：
GitHub Appの秘密鍵：差し替え済み。
 8月のインシデントで、この秘密鍵は8月27日に読み取られました。GitHubの監査ログとシークレット管理サービスのバージョンの時刻によると、秘密鍵は8月31日に差し替えられており、悪用可能だった期間は約4日間です。このAppはZeaburのGitHub organizationにインストールされており、秘密鍵を保持していればorganization内のすべてのリポジトリを読み取れます。
設定リポジトリ内の平文の認証情報：差し替えていない。
 10月14日に攻撃者が最初に使用したAWSキーとクラスター管理トークンは、8月27日の時点ですでに設定リポジトリに平文で存在していました。8月のインシデント後、当社は秘密鍵のみを差し替え、これらの認証情報は差し替えておらず、10月15日のインシデント対応で初めて無効化しました。したがって、秘密鍵が差し替えられた後でも、8月27日から31日の間に何者かがリポジトリの内容を取得していれば、その中の認証情報は10月の時点でも有効なままでした。
その他の間接的な手がかり：
攻撃者が読み取ろうとした内部シークレットの名前の一部は、別の内部リポジトリにのみ存在します。攻撃者は2つのリポジトリの内容を同時に保持していた可能性があり、これはAppの秘密鍵が持つorganizationレベルの権限と一致します。
10月14日 01:36より前に、共有クラスターとAWSで有効な認証情報が使用された記録はなく、のちに認証情報を不正利用したIPもZeabur APIにログインしていません。これは「リポジトリ内の認証情報のみを保持していた」状況と一致します。
裏付けにならない手がかり：
 8月のインシデントと今回のインシデントで、攻撃者のIPに重複はありません。
証拠収集の進捗：
 当社はGitHub Supportに関連する記録を申請しています。8月27日から31日の間にこのAppが発行したアクセストークン、設定リポジトリのcloneとダウンロードの記録、8月30日と9月2日に従業員の認可で設定リポジトリをダウンロードした送信元が含まれます。本記事の更新時点で、まだ回答を得ていません。記録を入手するまで、この経路は推測にすぎません。従業員の認可によるダウンロードが別の取得経路であった可能性も否定できません。
