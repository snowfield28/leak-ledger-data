cloudlinux-release update adds the TuxCare ELS repositories
Subscribe
Monitoring
 - 
Starting November 10, a 
cloudlinux-release
 update rolls out gradually to CloudLinux OS 7–10 and CloudLinux OS for Ubuntu servers. The update adds the TuxCare Extended Lifecycle Support (ELS) repositories for alt-PHP, alt-Python, alt-Node.js and alt-Ruby. Where 
rhn-client-tools
 is too old to fetch the token these repositories need, it also brings a newer one.
TuxCare ELS will become the only source of 
alt-*
 updates, CVE fixes included. That switch hasn't happened yet: we'll announce it in advance, once most servers have these repositories switched on. After it, a server with them off gets no new 
alt-*
 updates.
Registered with CLN and actively updating:
 nothing to do. The ELS repositories switch on by themselves, usually within a minute of the update.
No CLN registration:
 the ELS repositories stay off, and yum, dnf and apt keep working with your other repositories.
Broken registration or lapsed licence:
 the ELS repositories answer 403 Forbidden. On CloudLinux OS 7–10 that stops the whole yum or dnf update; on Ubuntu, 
apt-get update
 exits with an error. Run 
rhn_check
 to fetch a fresh token. If that doesn't help, fix the registration or renew the licence, or disable the ELS repositories by hand: the update leaves a repository you disabled alone.
Outbound allowlist:
 allow HTTPS to repo.alt.tuxcare.com and rollout.alt.tuxcare.com, or updates can fail the same way as with a 403.
Your own mirror:
 add the four ELS repositories and the 
alt-common
 repository to it, and point the repository files at it. Mirror access is granted per IP address: ask your account manager or 
sales@tuxcare.com
. The update leaves a repository that points at another host alone.
Excludes and version locks:
 with 
rhn-client-tools
 excluded or locked, the server can't take this update, and on CloudLinux OS 7–10 the whole yum or dnf update stops. Remove the exclude or lock before you update. Keep 
alt-common-release
 and 
alt-php-els-meta
 out of any 
alt-*
 excludes.
CloudLinux OS for Ubuntu:
apt-get upgrade
 keeps the update back; run 
apt install rhn-client-tools cloudlinux-release
 instead. On servers still on 
rhn-client-tools
 2.12 it also replaces 
python3-rhnlib
 and 
rhnlib
; nothing else is removed. We recommend it rather than 
apt full-upgrade
, which may also propose removing 
alt-phpXX-fpm
 packages for reasons unrelated to this update.

The KernelCare livepatch for CloudLinux 8 is released
 (K20261105_0055, production feed since 2026-11-06 08:50 UTC). Run 
kcarectl --update
. We made it ahead of the vendor.
Technical summary
The bug is in 
sock_gettstamp()
 in 
net/core/sock.c
. This is the kernel handler for the 
SIOCGSTAMP
 and 
SIOCGSTAMPNS
 ioctls, which return the time a packet arrived.
- On first use the handler sets a flag in the socket flags word without the socket lock.
- The flag update is not atomic. A 
bind()
 on the same UDP socket at the same moment can lose its own update to the same word.
- The lost flag is 
SOCK_RCU_FREE
. It tells the kernel to wait for readers before it frees the socket.
- Without it, the socket is freed at once on close, while the UDP receive path can still use it. This is a use-after-free.
- The fix takes the socket lock in 
sock_gettstamp()
, only when the flag must be set.
- Present since Linux 2.6.12, so all supported kernels are affected.
Crash signature on the attacked CloudLinux 8 server:
- 
WARNING ... at net/ipv4/af_inet.c:153
 and 
:156
 in 
inet_sock_destruct
- then a NULL pointer dereference in 
udp_destruct_common
 (socket close) or in 
__sk_mem_raise_allocated
 called from 
__udp_enqueue_schedule_skb
 (UDP receive)
- with 
kernel.panic_on_oops = 1
 each crash rebooted the server
What the KernelCare livepatch does
- Ports the upstream fix: take the socket lock around the flag update. Small change, no data structure change.
- LibCare is out of scope (kernel bug).
Mitigation
There is no practical mitigation.
 Install the livepatch where it is released.
- No sysctl or kernel option turns the affected code off. Any user who can open a UDP socket can reach it.
- A firewall does not help. The trigger is local socket calls and does not pass through iptables or nftables.
- An SELinux policy can block the two ioctls, but control panels require SELinux to be disabled on CloudLinux. Not a usable option for most servers.
- Restricting or suspending untrusted local accounts lowers the risk until the livepatch is installed.

On 21 October 2026 the Node.js project published security releases for the 22.x, 24.x and 26.x lines (v22.23.4, v24.22.1, v26.12.1). They fix 10 vulnerabilities, and the highest severity is High.
