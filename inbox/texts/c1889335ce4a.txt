PHP2Shell exploitation observed: packet-to-process RCE evidence
24 October 2026 · UTC · evidence acquired through 19:26–19:31 across six sensors
Case evidence dataset:
 Per-case HTTP packet captures and selected Apache, PHP, Tetragon, and signal records for all 35 confirmed shells (
A01
–
A03
, 
B01
–
B32
) are published in 
2026-10-24-rce-evidence/
.
Technical summary
Target-side packet captures and Tetragon process events correlate 
35 complete execution-stage HTTP POSTs with 35 
/bin/sh
 starts directly parented by Apache workers
 (
uid=33
) across three PHP targets. Three shell events followed traffic from 
15.204.59.70
 on T1; 32 followed traffic from 
162.35.99.94
 on T1, T2, and T3. These are two source-address clusters, not an attribution to two actors.
The requests used a four-stage multipart chain, sometimes with retries: memory pressure, memory disclosure through an oversized 
PHPSESSID
, further memory pressure, then a target-adjusted execution stage. Fifty-two disclosure-sized cookies were logged; 51 complete responses were reconstructed in packet captures and acknowledged by the client. Representative complete chains from both source clusters and all three successful targets shared byte-identical A1/B1/A2 bodies. The B2 body varied with the target's leaked address range and the shell command, supporting the 
published leak-guided ASLR technique
 rather than a new primitive. The traffic closely matches the public HTTP-only PoC family; packet evidence does not identify the exact client or revision used.
Evidence and scope
The reviewed targets ran PHP 8.4.26 under single-worker Apache 
mod_php
 with a 128 MiB PHP memory limit. The relevant PHP errors occurred during request startup (
Unknown on line 0
), before application code, consistent with a PHP-engine vulnerability rather than a flaw in a particular CMS. All confirmed execution-stage requests used plaintext HTTP/80. 
T1
–
T3
 label the three targets throughout this report.
The targets were disposable 
phpot
 honeypots presenting ordinary PHP-backed pages. The sensor records bidirectional network packets, Apache requests and worker PIDs, PHP errors, and Tetragon process/kernel events. We joined the packet flows to application and process records by source port, time, worker identity, and request sequence; no single alert or HTTP status was treated as proof of execution.
The acquired snapshot contains 3,459 sealed segments and 10,948 manifest-listed files (11.21 GB); all listed sizes and SHA-256 values matched their local copies, and the parsed Apache/Tetragon JSONL records had no malformed lines. The latest sealed window on each sensor ended between 19:26 and 19:31 UTC. Counts below refer to this fixed snapshot.

15.204.59.70
The source began path probing at 13:47, sent memory-pressure requests by approximately 15:16, and produced its first confirmed Apache-parent shell at 15:35. Two further shells followed at 16:04. Episode B — 
162.35.99.94
The source appeared at 16:36 with disclosure-sized responses, cycled through repeated OOM/leak/crash attempts around 16:44–16:46, and produced its first confirmed shell at 16:46. Tetragon recorded 32 Apache-parent shell starts through 18:57: 19 on T2, ten on T3, and three on T1. Commands changed among PHP CLI,

The target-dependent final-stage bodies and command changes distinguish this episode from A operationally, while the byte-identical first three request bodies link both episodes to the same exploit template.
Relationship between episodes:
 The shared template, boundary, body hashes, and stage order do 
not
 establish shared control. Nor do different source IPs and proof commands establish separate actors. The defensible finding is two source-address episodes using closely related tooling.

attempt indicators, not confirmed RCE sources

HTTP fingerprint
The successful chains used HTTP/1.1 multipart POSTs to 
/
 and 
/index.php

User-Agent
, and a ten-character 
C

q...=v

Memory disclosure and ASLR adjustment
Apache recorded 52 disclosure-sized cookies: three for A on T1 and, for B, four on T1, 29 on T2, and 16 on T3. Each decoded to 819,200 bytes. The decoded values were not ordinary session IDs: they contained repeated aligned, pointer-like 64-bit words, including a dominant word repeated 1,095 times in representative leaks. Matching the cookie's SHA-256 from Apache to target-side PCAPs gave 
51 complete responses with zero captured response gaps and a client ACK through the response end
 (T1 7/7, T2 28/29, T3 16/16). The remaining T2 capture begins mid-response; Apache recorded the cookie, but its complete packet delivery is not established by that file.
The dominant disclosed pointer differed in absolute value across representative T1, T2, and T3 leaks. An address-like word in their corresponding B2 bodies maintained the same relative difference from that value across the three targets. Along with the request sequence, this supports leak-guided adjustment to each target's randomized memory layout rather than one hard-coded address accidentally working everywhere. The public 
9bie HTTP-only PoC
 uses the same type of relative calculation and request roles; 
Wiz's PHP2Shell research
 describes the underlying PHP upload-progress/disclosure family. The observed chain is consistent with 
CVE-2026-109618
; these records do not establish use of a distinct CVE-2026-109619 path.
The public 
exploit.py
 revision examined on 24 October
 filters disclosed pointers below 
0x7f0000000000
. The early successful chains had no pointer-like words above that threshold in their observed cookies, so an unchanged run of that revision would not parse those leaks. Two later T3 cookies 
did
 contain qualifying pointers. The traffic therefore does not support a blanket claim that every successful run required a modified PoC; a small change, another revision, or a different client could explain the early chains. Packet captures cannot identify which implementation was used.
