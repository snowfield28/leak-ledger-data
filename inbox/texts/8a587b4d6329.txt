wfx-loot campaign pushes CI secret stealer to tens of thousands of repositories
Starting on November 10, a threat actor used stolen GitHub credentials to push a malicious workflow payload into tens of thousands of repositories. The payload steals GitHub Actions secrets and cloud credentials. The payload has proliferated into at least one Packagist and one Golang package through automated publishing triggers, but the threat actor appears to be targeting CI secrets rather than attempting to proliferate through the supply chain. 
Based on data we've currently collected:
4,837 compromised accounts opened probe pull requests in 61,764 repositories.
At least 1,835 repositories ran the payload and have had credentials exfiltrated. 
At least 50 compromised users appear to publish packages for ecosystems including npm, Go, Packagist, PyPI or crates. 
We're tracking this campaign as 
wfx-loot
 based on the threat actor's name for the malware and the term used for stolen secrets.
‍
Who is affected
You may be affected if any of these appeared in a repository you can write to on or after November 10:
A 
wfx-docs
 branch, or a pull request titled 
docs: dependency audit notes
Commits titled 
ci: refresh build cache
, 
chore: add ci helper
 or 
chore: add dependency audit workflow
Short-lived branches named 
chore/
 followed by eight random characters
GitHub search returns 61,839 
docs: dependency audit notes
 pull requests, opened between November 10, 12:45 UTC, and November 11, 15:00 UTC. That pull request is only a probe, and is followed by commits that carry the real payload. If the probe ran, that user is compromised, even if the workflow stage did not run. 
10,431 of the pull requests went into repositories the account doesn't own, reached through collaborator or organisation access.
92% of them are still open, which suggests most owners haven't noticed.
We've identified indications that the payload ran in at least 1,806 repositories, but this number may understate impact. The run log was deleted in impacted repositories, meaning the threat actor has likely collected the credentials and covered its tacks. Most of the rest had nothing pushed after the probe, or the infected workflow didn't run due to configurations or the permissions of the compromised user.
If the payload ran in your repository, assume every secret and cloud role available to its workflows is compromised.
We've also observed this campaign entering published packages through automated publishing triggers. Malicious packages we've identified to date include:
Packagist 
digitalelvis/neuronai-studio
 version 3.14.3. Treat any machine that installed or opened either version as compromised.
Go module 
github.com/onuragtas/docker-env
 v1.0.278 and v1.0.280: these tags contain the payload in a GitHub Actions workflow file only. The Go source and release binaries are unchanged, and Go builds never run workflow files, so consumers of the module may not have been affected, but we recommend removing these packages anyway. 
What happened
Starting at approximately 12:45 UTC or November 10, the threat actor started using compromised GitHub tokens to spread the malware. For each repository a stolen GitHub token can write to, the threat actor:
Probes
 - The threat actor opens a 
docs: dependency audit notes
 pull request from a 
wfx-docs
 branch, which confirms write access.
‍
Pushes the payload - 
The threat actor uses one of three variants:
Workflow injection: 
ci: refresh build cache
 adds about 1,500 lines to an existing workflow.
Install hook: 
chore: add ci helper
 adds a 
.ci-xxxxxx.sh
 script and a 
postinstall
 hook in 
package.json
 that runs it on any 
npm install
Throwaway branch: c
hore: add dependency audit workflow
 adds 
.github/workflows/build-audit-xxxxxx.yml
 on a 
chore/xxxxxxxx
 branch.
Cleans up
 - the threat actor reverts within at most one minute and deletes the workflow run, along with its logs. A missing run number in the workflow's history is often the only trace.

What it steals
The payload is a single shell script of about 1,500 lines. The same script is used in all three delivery variants. It works in four stages: collect, escalate, persist and exfiltrate. Configuration flags at the top of the script switch individual features on and off. This section describes everything the script can do, but some of the exfiltration features were turned off in this campaign. 
The script is heavily commented, not obfuscated and self-designates as "wfx" in logs and variable names. 
Collect
. The payload collects credentials from every source available on the runner:
GitHub Actions secrets and variables, the workflow 
GITHUB_TOKEN
, and the OIDC and Actions runtime tokens.
The full runtime environment, plus a filtered copy of variables matching 
token
, 
secret
, 
pass
, 
cred
, 
aws
, 
azure
, 
gcp
, 
openai
, 
anthropic
, 
stripe
 and dozens of other keywords.
Credential files from well-known paths including AWS, Azure, GCP, Docker, Kubernetes, npm, PyPI, Git, SSH, GPG, Vault and Terraform.
Credentials for AI providers and AI developer tools, including OpenAI, Anthropic/Claude, Gemini, Hugging Face, Cursor, Copilot, Codex, Continue, Codeium, Aider, Weights & Biases and Ollama.
Shell histories for bash, zsh, mysql, psql, python and node.
Every .
env
, 
.pem
, .
p12
, 
.jks
, 
.kdbx
 and 
kubeconfig
 file under 
$HOME
, searched recursively.
The environment and memory of running processes on the runner, prioritizing 
Runner.Worker
 and 
Runner.Listener
. It extracts JWTs, GitHub PATs, AWS keys and AI provider tokens.
On self-hosted runners only:
AWS, GCP and Azure instance metadata credentials
Docker container state
the runner's RSA parameters
systemd units
A snapshot of the repository, the files in it that match a catalog of secret patterns, the last 100 commits, and recent workflow artifacts
Escalate
. The payload uses the collected credentials to get deeper cloud access:
OIDC exchange
 - It mints GitHub OIDC tokens for AWS, GCP and Azure audiences and exchanges them for cloud sessions.
AWS
 -It chains into other IAM roles it finds in the repository, then calls 
iam:CreateAccessKey
 to create long-lived credentials for IAM users.
GCP
 - It signs JWTs with service account keys using a dependency-free Python RSA implementation and exchanges them for access tokens. It then lists projects and service accounts, and calls 
generateAccessToken 
and 
signJwt
 to impersonate service accounts.
Azure
 - It exchanges OIDC tokens or client secrets for management tokens and lists subscriptions and Key Vaults. It also pivots with FOCI refresh tokens, replaying cached Azure CLI refresh tokens against first-party Microsoft client IDs to get Graph, ARM and Key Vault tokens.
Vault and Kubernetes - 
It replays OIDC tokens against HashiCorp Vault and against Kubernetes API servers found in kubeconfig files.
Persist
. The payload takes three actions designed to outlast credential rotation:
Branch protection bypass
 - Early in the run, before most collection, the payload posts forged 
success
 status checks against the commit SHA, using the context names of the repository's required checks. Branch protection matches on the context name, not on the app that posted it, so the forged checks clear merge gates while the payload is still running.
‍
AWS trust policy rewrite 
- It sets the chained role's trust policy to 
"Principal": {"AWS": "*"}
, which opens the role to any AWS account.
‍
Azure federated identity injection
 - With a Microsoft Graph token, it adds new federated identity credentials, named 
wfx-ci-…
, to Azure AD applications, pointing back to the compromised repository. Any workflow in that repository can then authenticate to Azure without a stored secret, even after every token has been rotated.
Exfiltrate
. The payload packs everything into a gzipped tarball. The script supports several delivery channels, three of which use GitHub's own infrastructure to get around network egress restrictions:
Actions Cache API
 - It stores the tarball as a cache entry, retrievable later with a matching key. 
Step summary 
- For archives under 700 KB, it base64-encodes the tarball into the workflow step summary between 
<!--WFX-BEGIN-->
 markers.
‍
Artifact upload
 - It uploads the tarball as a workflow artifact named 
wfx-loot-<run id>
.
The other channels are:
a direct HTTP POST to the callback server, retried with increasing back-off
a secondary callback URL
an AES-encrypted copy committed to the repository
base32-encoded output written to the workflow run log
exfiltration via Telegram Bot
In this campaign, the payload was configured to send data only by HTTP POST to 
194.150.166[.]244:8080/exfil
 or 
18.143.168[.]96:8080/exfil
:
The cache, step summary and artifact channels only run when the private-repository flag is set, and the deployed configuration turns it off
The encrypted-commit fallback and the run-log channel are disabled
No secondary callback is set
If you are checking an affected repository, the absence of 
wfx-loot
 artifacts, 
wfx-
 cache entries or 
WFX-BEGIN
 step summaries does not mean data was not taken. The run itself is usually deleted based on our data. A missing run number on the attacker's commit is the more reliable sign that the payload ran. The existence of dedicated configurations for private repositories suggests that the payload may be being deployed in private repositories as well as the public ones we can identify. 
Overlap with October GhostAction activity
Accounts impacted in this wave cross over with the October GhostActions wave, matching known GhostActions indicators:
Secret-scanning workflows (
security-audit.yml
, 
audit.yml
, 
ci-check.yml
 and similar) that send keys found in the repository and its git history to 
193.32.204[.]199
.
A developer-machine stealer: 
public/fonts/fa-solid-400.woff2
, which is JavaScript, not a font, plus a hidden VS Code task that runs it when the folder is opened. It takes 
~/.git-credentials
, SSH keys, npm, PyPI, AWS and Claude credentials, and installs a cron job tagged 
#ghc2
 that polls 
193.32.204[.]199:8080
 for commands. 
Accounts hit by GhostAction in October were significantly more likely than baseline to be impacted by wfx-loot. In more than 100 repositories, wfx-loot was injected into the GhostActions workflow files.. Despite the overlap in accounts, we assess that these are distinct campaigns likely carried out by different threat actors. The infrastructure, tooling and tradecraft differ, and stolen credentials often end up in the hands of several threat actors. We've also noticed Indonesian-language comments in some newer versions of the malware that are the result of a hasty edit to add Telegram exfiltration. We've never observed Indonesian artefacts in GhostAction activity.
